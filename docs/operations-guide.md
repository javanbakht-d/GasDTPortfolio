# راهنمای عملیات — نصب، پیکربندی، استقرار و بازیابی (NIGC-DTG)

این سند چگونگی اجرا، پیکربندی موتور یادآوری/دستیار، استقرار تولید و بازیابی از پشتیبان را پوشش می‌دهد.

## ۱. نصب و اجرا (محیط توسعه)

```bash
# پیش‌نیاز: bun ≥ 1.3
bun install                     # نصب وابستگی‌ها
bun run db:push                 # ایجاد/به‌روزرسانی پایگاه داده (SQLite در db/custom.db)
bun scripts/seed.ts             # داده پایه: ۳۷ گام، ۱۶ نقش، واحدها، کاربران، اسناد، KPIها
bun scripts/seed-upgrade.ts     # تنظیمات موتور یادآوری/گزارش‌های خودکار/اولویت (افزودنی)
bun run dev                     # سرور روی پورت 3000 — موتور یادآوری خودکار با سرور بوت می‌شود
```

کاربران نمونه (پیش‌فرض seed — **در استقرار واقعی فوراً تغییر دهید**): admin / sec.admin / secretary / council / itc.mgr / itc.liaison / auditor / viewer — رمز همه: Nigc@1405
دبیر شورا برای تجربه کامل میزکار روزانه: کاربر secretary یا sec.admin.

## ۲. پیکربندی موتور یادآوری و گزارش‌های خودکار

همه پارامترها از **تنظیمات و راهبری سامانه → تب «یادآوری‌ها و گزارش‌های خودکار»** (مجوز settings:manage) قابل تغییرند. کلیدهای اصلی:

| کلید | پیش‌فرض | معنی |
|------|---------|------|
| reminders.enabled | true | روشن/خاموش‌کردن کامل موتور |
| reminders.tickIntervalSec | 60 | فاصله چرخه یادآوری (ثانیه) |
| reminders.preDueCriticalDays | 7 | یادآوری پیش از سررسید — اولویت بحرانی |
| reminders.preDueHighDays | 5 | — اولویت زیاد |
| reminders.preDueNormalDays | 3 | — سایر |
| reminders.overdueEscalateDays | 3 | تشدید/ارجاع معوق به دبیرخانه |
| reminders.followUpDefaultDays | 3 | پیش‌فرض «زمان پیگیری بعدی» |
| reminders.quietStart / quietEnd | 21 / 7 | ساعات سکوت اعلان‌های عادی (تهران) |
| reminders.quietBypassCritical | true | استثنای موارد بحرانی از سکوت |
| digest.morningEnabled / morningTime | true / 07:30 | گزارش صبحگاهی دبیر شورا |
| digest.eodEnabled / eodTime | true / 18:00 | خلاصه پایان روز |
| digest.weeklyEnabled / weeklyDay / weeklyTime | true / 4 / 16:00 | خلاصه هفتگی (۴=پنجشنبه) |
| priority.weights | {urgency:35,…} | وزن‌های مدل اولویت (جمع باید ۱۰۰ باشد) |

تغییر تنظیمات در سوابق ممیزی (SETTING_CHANGE) ثبت می‌شود.

## ۳. کانال ایمیل (فعال‌سازی اختیاری)

پیش‌فرض صادقانه: بدون SMTP، پیام‌ها در `EmailOutbox` با وضعیت PENDING و blockedReason می‌مانند و «ارسال‌شده» جعل نمی‌شود. برای فعال‌سازی در استقرار تولید:
1. کلیدهای `smtp.host`، `smtp.port`، `smtp.user`، `smtp.pass` (Secret سمت سرور — نه در کد) را در تنظیمات تعریف کنید
2. sender را در `queueDigestEmails` (src/lib/scheduler-engine.ts) وصل کنید (مثلاً nodemailer)
3. صف موجود به‌طور خودکار برای پیام‌های جدید استفاده می‌شود؛ گزارش‌های انباشته در پنل سلامت قابل رصدند

محرمانگی: خلاصه‌های ایمیلی فقط عنوان/اهمیت + دعوت به ورود — جزئیات محرمانه در ایمیل نمی‌آید (سیاست `ai.confidentialPolicy`).

## ۴. استقرار تولید (توصیه‌شده)

- **پایگاه داده:** SQLite برای sandbox است؛ برای عملیات، PostgreSQL توصیه می‌شود (طرح schema سازگار است) + پشتیبان‌گیری روزانه (pg_dump/cron)
- **زمان‌بند:** در این نسخه موتور با خود سرور بوت می‌شود (instrumentation). برای مقیاس عملیاتی، اجرای worker جداگانه با همان `runFullTick()` (صف پایدار مانند Redis/BullMQ یا cron سیستم با فراخوانی POST /api/scheduler) — جزئیات در docs/reminder-engine.md
- **متغیرهای محیطی:** DATABASE_URL، و هر Secret مربوط به SMTP — هرگز در مخزن کد
- **اولین قدم‌های پس از استقرار:** تغییر رمز همه حساب‌ها، تعریف کاربران واقعی، تأیید/تنظیم `program.baselineDate` از گردش کار «تاریخ مبنای برنامه» (با علت و مرجع تأیید)، تنظیم ساعت گزارش صبحگاهی با ساعت کاری سازمان

## ۵. پشتیبان‌گیری و بازیابی

**پشتیبان دستی (آزموده‌شده):**
```bash
TS=$(date +%Y%m%d-%H%M); mkdir -p backups/backup-$TS
cp db/custom.db backups/backup-$TS/custom.db
tar czf backups/backup-$TS/code-snapshot.tar.gz --exclude=node_modules --exclude=.next --exclude=backups --exclude=db .
```

**بازیابی:** توقف سرویس → جایگزینی `db/custom.db` با نسخه پشتیبان → اجرای سرویس. آزمون integrity: `PRAGMA integrity_check` (در آزمون پذیرش ۷ = ok). برای SQLite هم‌زمان با سرویس فعال بازیابی نکنید.

**پشتیبان دوره‌ای خودکار:** هنوز پیاده نشده (نیازمند تصمیم عملیات) — پیشنهاد: افزودن jobKey=CLEANUP-گونه‌ای به زمان‌بند که روزانه از فایل DB کپی زمان‌بندی‌شده بسازد، یا cron سیستم خارج از اپ. تا تصمیم، پشتیبان دستی را به‌صورت هفتگی اجرا کنید.

## ۶. پایش سلامت و عیب‌یابی

- **پنل:** تنظیمات → «سلامت و قابلیت اعتماد دستیار» (آخرین اجرا، شکست‌های ۲۴ ساعت، صف ایمیل، DB، دستیار) — بازخوانی هر ۳۰ ثانیه
- **API:** `GET /api/scheduler` (admin) · اجرای دستی: دکمه در همان پنل یا `POST /api/scheduler`
- اگر «زمان‌بند زنده نیست» نمایش داده شد: سرور به‌تازگی ری‌استارت شده یا tickIntervalSec خیلی بزرگ است؛ لاگ `dev.log` را برای `[scheduler]` ببینید
- شکست اجرا → اعلان SCHEDULER_ALERT برای ادمین‌ها (بدون سکوت بی‌صدا)
- خاموش‌کردن دستیار هوشمند بدون آسیب به سایر قابلیت‌ها: تنظیم `ai.enabled=false`

## ۷. داده‌های آزمون و بازگشت

برای آزمون یادآوری بدون انتظار واقعی: یک اقدام آزمایشی با سررسید نزدیک/گذشته ثبت کنید (اقدامات و تعهدات → اقدام جدید) و از دکمه «اجرای دستی چرخه زمان‌بند» در پنل سلامت استفاده کنید؛ سپس رکورد آزمایشی را ببندید (CLOSED) تا از فهرست فعال خارج شود (تاریخچه حفظ می‌شود).
