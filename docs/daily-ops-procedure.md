# دستورالعمل عملیاتی روزانه — پایش عملکرد کل سامانه NIGC-DTG

**نسخه:** ۱٫۰ | **تاریخ:** ۱۴۰۵/۰۸/۰۸ | **مالک فرایند:** مدیر سامانه (SYSTEM_ADMIN)
**دامنه:** سامانه تولیدی `https://gasdt.vercel.app` + دیتابیس Supabase (فرانکفورت) + موتور یادآور (cron-job.org)
**زمان اجرای روزانه:** ۵ دقیقه (خودکار: صفر دقیقه)

---

## ۱. هدف و دامنه

این دستورالعمل تضمین می‌کند که هر روز، **پیش از شروع ساعت کاری**، سلامت و عملکرد کل سامانه بررسی شده باشد:

| مؤلفه | چه چیزی پایش می‌شود |
|---|---|
| دسترس‌پذیری | پاسخ HTTP سامانه و زمان پاسخ |
| دیتابیس | اتصال، تأخیر، حجم (سهمیه ۵۰۰MB پلن رایگان)، اتصالات فعال |
| موتور یادآور | تازگی تیک، خطاها، بسامد اجرا در ۲۴ ساعت |
| اعلان‌ها | رکورد خراب و معوق |
| صف ایمیل | رکوردهای در صف / ارسال‌شده / خراب |
| امنیت | قفل bootstrap، رخدادهای دسترسی مردود (الگوی حمله) |
| داده‌ها | شمارش کاربر/اقدام/سند/شاخص برای تشخیص رشد غیرعادی |

---

## ۲. معماری پایش — چهار لایه دفاعی

```
لایه ۱  cron-job.org        هر ۵ دقیقه  → تیک موتور یادآور (تاریخچه سبز/قرمز خودکار)
لایه ۲  daily-check API     درخواستی   → گزارش ۱۱ بررسی جامع در یک فراخوانی
لایه ۳  گزارش خودکار روزانه هر روز ۰۹:۰۰ تهران → گزارش فارسی در همین چت (عامل هوشمند)
لایه ۴  داشبوردهای ابری     هفتگی      → Supabase (پشتیبان/سهمیه) + Vercel (ترافیک/خطاها)
```

لایه ۲ و ۳ در این دستورالعمل راه‌اندازی شده‌اند. اگر لایه ۳ (گزارش خودکار) روزی قطع شود، لایه ۲ (فراخوانی دستی) طبق بخش ۴ جایگزین می‌شود.

## ۳. فراخوانی گزارش روزانه (لایه ۲)

**آدرس:** `https://gasdt.vercel.app/api/system/daily-check?key=<CRON_SECRET>`

* کلید همان `CRON_SECRET` گام ۳ راهنمای استقرار است (همان کلیدی که cron-job.org استفاده می‌کند).
* بدون کلید یا با کلید نادرست: `403` — گزارش تولید نمی‌شود.
* گزارش **فقط‌خواندنی** است و هیچ رکوردی در دیتابیس نمی‌نویسد.

**نمونه خروجی (ساده‌شده):**

```json
{
  "ok": true,
  "overall": "PASS",            // PASS | WARN | FAIL
  "summary": "همه بررسی‌های ضروری سبز است (10/10)",
  "region": "fra1",             // ناحیه اجرای Function — باید fra1 باشد
  "checks": [
    { "key": "db_connectivity",  "status": "PASS", "value": "34ms",  "threshold": "..." },
    { "key": "scheduler_freshness", "status": "PASS", "value": "2 دقیقه پیش", "threshold": "..." },
    ...
  ],
  "metrics": { "dbSizeMb": 12.4, "dbQuotaPct": 2, "lastTickAgeMin": 2, ... }
}
```

**قاعده تفسیر:**
* `overall: PASS` → سامانه سالم است؛ کار دیگری لازم نیست.
* `overall: WARN` → سامانه کار می‌کند اما یک بررسی زرد است؛ همان روز علت را از ستون `detail` و بخش ۶ بیابید.
* `overall: FAIL` → **حادثه**؛ بلافاصله بخش ۶ (Playbook) را اجرا کنید.
* `region` هر چیزی غیر از `fra1` بود → در Vercel: Settings → Functions → Region را بازبینی و Redeploy کنید.

## ۴. چک‌لیست دستی روزانه (۵ دقیقه) — نسخه جایگزین/مکمل

اگر گزارش خودکار روزی نیامد یا خواستید خودتان بررسی کنید، به همین ترتیب:

| گام | کار | روش | نتیجه مورد انتظار |
|---|---|---|---|
| ۱ | باز کردن سامانه | مرورگر → `https://gasdt.vercel.app` | صفحه فارسی بارگذاری شود (<۳ ثانیه) |
| ۲ | ورود مدیر | لاگین با حساب admin | داشبورد با داده‌های واقعی |
| ۳ | گزارش جامع | فراخوانی آدرس بخش ۳ (کروم کافی است) | `"overall": "PASS"` |
| ۴ | تاریخچه کرون | سایت cron-job.org → job «NIGC-DTG Reminder Tick» | آخرین اجراها سبز، Next run زمان آینده |
| ۵ | زمان‌بند داخل سامانه | تنظیمات دستیار → کارت سلامت | «زمان‌بند زنده است — تیک خودکار فعال» |
| ۶ | پشتیبان دیتابیس | Supabase → Database → Backups | آخرین backup ≤ ۷ روز |
| ۷ | ثبت نتیجه | یادداشت یک‌خطی (تاریخ + PASS/FAIL) | سوابق قابل ردیابی |

> نکته: اگر همیشه از لایه ۳ (گزارش خودکار) استفاده می‌کنید، همین چک‌لیست را **هفته‌ای یک‌بار** اجرا کنید.

## ۶. Playbook حادثه — واکنش به وضعیت‌های قرمز

### سناریو A — «تازگی تیک» قرمز (زمان‌بند مرده)
1. cron-job.org → job → تب Logs: آیا اجراهای اخیر **قرمز** هستند یا اصلاً اجرا نشده؟
2. اگر قرمز: اجرای دستی «Run now» → اگر خطا 403 بود، `CRON_SECRET` در URL و در Vercel یکی نیستند (گام: متغیر را در Vercel ببینید و URL را همگام کنید).
3. اگر اجرا نمی‌شود: cron-job.org را بررسی کنید (فعال بودن job، سهمیه حساب)؛ راه موقت: فراخوانی دستی `https://gasdt.vercel.app/api/system/cron-tick?key=<CRON_SECRET>` تا رفع شود.
4. اگر cron سبز است ولی تیک ثبت نمی‌شود → مشکل سمت سرور است؛ لاگ‌های Vercel → Deployments → Runtime Logs.

### سناریو B — «اتصال دیتابیس» قرمز
1. Supabase → آیا پروژه **Paused** شده؟ (پلن رایگان پس از ۱ هفته بی‌فعالیتی متوقف می‌شود — با تیک ۵ دقیقه‌ای نباید رخ دهد) → Restore را بزنید.
2. آیا سهمیه (500MB / egress) پر شده؟ → داشبورد → Usage.
3. DATABASE_URL در Vercel دست‌نخورده؟ (کسی تغییری نداده باشد)
4. پس از رفع، گزارش روزانه را دوباره فراخوانی کنید تا PASS شود.

### سناریو C — «حجم دیتابیس» زرد/قرمز
1. Supabase → Table Editor → جداول حجیم (معمولاً SchedulerRun و Notification و AuditLog).
2. SchedulerRun به‌طور خودکار تا ۳۰ روز نگه‌داری می‌شود؛ اگر بیشتر شد، تیک را بررسی کنید.
3. در صورت نیاز، پاکسازی دستی رکوردهای قدیمی AuditLog (بیش از ۹۰ روز) با هماهنگی شورا.

### سناریو D — «دسترسی مردود» زرد/قرمز (احتمال حمله)
1. لاگ ممیزی داخلی سامانه → رخدادهای ACCESS_DENIED → منبع IP و نام کاربری.
2. اگر الگوی تکراری روی یک حساب است: آن حساب را موقتاً غیرفعال و رمز را بازنشانی کنید.
3. هیچ داده‌ای پاک نکنید — سوابق ممیزی مدرک است.

### سناریو E — پاسخ صفحه اصلی کند (≥۱۰s) یا خطا
1. Vercel → Deployments → آخرین deployment سبز است؟ اگر Red/Error → Rollback به نسخه قبلی.
2. Vercel → Runtime Logs → خطاهای 5xx را ببینید.
3. اگر Function Timeout → گزارش روزانه >۶۰ ثانیه طول کشیده؛ دوباره تلاش کنید و اگر تکرار شد، وضعیت دیتابیس را بررسی کنید (سناریو B).

### قاعده ارتقا
* قرمز که با Playbook تا **۱ ساعت** رفع نشد → ثبت رخداد و اطلاع به کمیته راهبری.
* هر قرمز تکرارشونده (۳ روز در هفته) → تحلیل ریشه‌ای، نه وصله روزانه.

## ۸. گزارش هفتگی و ماهانه

**هفتگی (۵ دقیقه — مثلاً شنبه‌ها):**
* اجرای کامل چک‌لیست دستی بخش ۴ (همه ۷ گام).
* مرور روند `dbQuotaPct` و `auditEvents24h` در گزارش‌های روزانه هفته.

**ماهانه (۱۵ دقیقه):**
* بازبینی سهمیه‌های بخش ۷ در داشبوردهای ابری.
* مرور حساب‌ها: کاربران غیرفعال، نقش‌های تغییرکرده (RBAC Matrix).
* تأیید اینکه BOOTSTRAP_TOKEN همچنان حذف است و رمزهای اولیه (`Nigc@1405`) هیچ حساب فعالی ندارند.
* یک بار «Run now» در cron-job.org برای اطمینان از سلامت قلاب بیرونی.

## پیوست — دستورات آماده کپی

```bash
# گزارش جامع روزانه (JSON کامل)
curl -s "https://gasdt.vercel.app/api/system/daily-check?key=<CRON_SECRET>"

# فقط وضعیت کلی و خلاصه
curl -s "https://gasdt.vercel.app/api/system/daily-check?key=<CRON_SECRET>" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print(d['overall'], '—', d['summary'])"

# تیک دستی موتور یادآور (موقت تا رفع مشکل cron)
curl -s "https://gasdt.vercel.app/api/system/cron-tick?key=<CRON_SECRET>"

# بررسی دسترس‌پذیری صفحه اصلی
curl -s -o /dev/null -w "HTTP:%{http_code} در %{time_total}s\n" https://gasdt.vercel.app
```

> **یادآوری امنیتی:** `<CRON_SECRET>` را در چت/ایمیل/مستند عمومی ننویسید؛ فقط در cron-job.org و Vercel نگهداری شود.
